### DDR-001 统一响应的 HTTP 状态码策略

- 日期：2026-10-28
- 阶段：Phase 0
- 背景：`{code, msg, data}` 的返回体很常见，但错误时 HTTP 状态码该返回 200 还是 4xx/5xx 存在分歧。
- 候选方案：
  - A：一律 HTTP 200，错误只体现在 body 的 `code`。前端只需判断一个字段。
  - B：协议层错误同步 HTTP 状态码，业务错误保持 200 + 业务码。
- 决策：选 B。
- 理由：全 200 会让网关、浏览器、APM 无法区分成功与失败，接口成功率永远是 100%，监控形同虚设。B 既保留 HTTP 语义，又让"业务规则不满足"（如批次状态不允许流转）不污染协议层错误统计。
- 代价：前端拦截器要同时处理 `res.code` 和 HTTP 错误分支，比 A 略复杂。
- 验证：`GlobalExceptionHandlerTest` 覆盖了"业务异常返回 200 + 2004"与"兜底异常返回 500"两条路径。

### DDR-002 异常处理收敛到全局

- 日期：2026-10-28
- 阶段：Phase 0
- 背景：原实现里每个 Controller 手工拼 `HashMap` 返回，错误靠 `if/else` 分散处理。
- 候选方案：
  - A：Controller 内 try-catch，逐接口返回。
  - B：`@RestControllerAdvice` 统一收敛，业务层只抛 `BizException`。
- 决策：选 B。
- 理由：错误格式在一处定义，新增接口零成本继承；业务代码可读性提升（不必被 try-catch 打断）；数据库约束异常（外键/唯一键）能统一翻译成用户可读文案。
- 代价：异常路径变"隐式"，新人需要知道 `BizException` 的存在才能正确使用。
- 验证：`DataIntegrityViolationException` 已能区分"唯一键冲突"与"外键引用"两种情况并给出不同文案。

### DDR-003 包结构按技术分层而非按业务模块

- 日期：2026-10-28
- 阶段：Phase 0
- 背景：项目有 11 张表、6 个业务模块，包结构可以按层（controller/service/mapper）或按模块（region/enterprise/batch）划分。
- 候选方案：
  - A：技术分层——`controller`、`service`、`mapper` 各自一个包。
  - B：业务模块——`region/`、`enterprise/`、`batch/`，每个模块内部自带 controller/service/mapper。
- 决策：暂选 A。
- 理由：单人开发、模块间调用较多（批次模块依赖企业模块），按层划分查找成本更低；Spring 的包扫描与 MyBatis 的 `@MapperScan` 也更直观。
- 代价：模块边界靠命名约定维持，规模再大容易出现跨模块直接调 Mapper 的情况。
- 验证：待 Phase 4 完成后回看是否出现跨模块调用混乱；若出现，再迁移到 B。
